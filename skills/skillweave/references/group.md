# 分（group）：把散技能归入类目，压低 L1 条目数

**目标**：第一级披露（Agent 的第一份菜单）= pack 入口层的**直接子项数**。散技能太多就把它变成
「两级选择」：先选类目 → 再选技能。

## 判据（先量）

```bash
python3 "$SW" layers "$PACK" --out /tmp/sw
```

看 L1 段：`入口层 <入口目录> 摆出 N 项（散技能 x + 类目 y）`，以及是否 `❌ 超上限 20`。
条目清单在 `layers.json` 的 `L1.menu_entries`。

## 两轴判据（先判轴，再定类目名）

**第一步只答一件事**：这个技能的主语是什么？

| 主语 | 落法 |
|---|---|
| **一个软件 / 工具 / 服务**（Hermes、Zotero、Dolt、docker…） | 类目按**用途**分（`install-*` / `maintain-*` / `troubleshoot-*` / `using-*`） |
| **一类任务 / 学科 / 项目**（SAXS 批处理、记账勾稽、Obsidian 整理…） | 类目按**主题**分（直接用学科/项目名） |

不要从技能名里抠关键词当类目（「名字里有 hermes 就归 hermes」这类机械判法是**不通过**的）；
判据是技能**正文在教什么**，至少读它的「什么时候用」一节。

## 类目命名

- 小写连字符、能独立看懂（`install-hermes-skills` 这类**技能名**别当类目名，太窄）。
- 同一个包里的类目数控制在 **3–8 个**；超过 8 个说明你在按技能名分，不是按用途分。
- 已有类目能用就别新建（`tree`/`layers` 先看现有分布）。

## 落盘

```bash
cp -R "$PACK" /tmp/pack-fix && cd /tmp/pack-fix
git mv skills/<散技能> skills/<类目>/<散技能>        # git 跟踪的用 mv 保历史
```

搬完**必须**同步正文里的路径引用（`references/…` 相对 skill 目录不变，但跨 skill 的转指路径会变），
再跑一次 `tree` 看 `broken` 有没有新增。

## 验收（四个数，改前 → 改后）

```bash
python3 "$SW" layers /tmp/pack-fix --out /tmp/sw-fix
```

1. **L1 条目数**（`入口层摆出 N 项`）下降到上限内或尽量接近；
2. **常驻 token**（`L1 常驻 …字符 ≈ …token`）**不上升**（类目不增加菜单成本，只把它分成两级）；
3. `broken` 引用没有新增（搬运别把引用搬坏）；
4. `orphans` 没有新增（`references/` 与 `SKILL.md` 的相对关系不能被破坏）。

## 反例

- 把**该独立的**技能塞进类目（它本来是另一个软件轴，硬塞让语义变糊）。
- 类目只能装 1 个技能（那不是类目，是套了个壳）。
- 只改目录不问「读的人还找得到吗」：入口层少了 10 项，但类目名是 `misc`。
